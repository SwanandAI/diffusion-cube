# Caching

There is no dedicated cache layer (no Redis, no CDN cache config, no `CACHES` setting) anywhere in this application. Two distinct, unrelated caching mechanisms exist instead, both in-application:

## 1. Generated-document content-hash cache

**Where**: [`lib/design-documents.ts`](../../../lib/design-documents.ts), used by `analysis-doc` and `executive-summary` modes via `lib/adoption-conversation.ts`.

**Mechanism**: `hashConversationState` computes a non-cryptographic djb2 hash over the current conversation + grid state. Before generating a new Analysis Document or Executive Summary, the client compares this hash against the stored `design_documents.content_hash` for the latest row of that `doc_type`. If unchanged, the stored row is served back directly — **no Anthropic API call is made**.

**TTL**: none — this is a content-equality cache, not a time-based one. It stays valid indefinitely until the conversation or grid actually changes.

**Invalidation strategy**: implicit, by content change — any new message or grid update changes the hash, which naturally "invalidates" the cache on the next generation request. There is no explicit `cache.delete`/invalidation call; a stale-content scenario is impossible by construction since the key *is* the content.

**Exception**: `draft` documents (pathway drafts, generated by `pathway-draft` mode) explicitly opt out. `insertDraftVersion` always sets `contentHash = String(Date.now())`, so every draft generation/revision is treated as new and always calls the model — drafts are meant to be genuinely regenerated on every request, not deduplicated.

## 2. Adoptions-list in-memory TTL cache

**Where**: [`lib/adoptions-cache.ts`](../../../lib/adoptions-cache.ts), used by `app/(app)/adoptions/page.tsx`, `app/contribute/ContributeGrid.tsx`, `components/Sidebar.tsx`'s recent-list.

**Mechanism**: a 60-second in-memory (per browser tab, not shared across tabs/users/server) cache of the caller's `designs` list (`fetchAdoptionsList`).

**TTL**: 60 seconds, but explicitly invalidated on any create/update rather than waiting out the TTL — so the effective staleness window is much shorter in practice for a single active tab.

**Invalidation strategy**: explicit — any adoption create/update calls the cache's invalidation directly. `fetchAdoption(id)` (a single row, used for deep links via `?open=<id>`) is **deliberately never served from this cache**, to guarantee freshness on a direct link open.

## Deprecated/inert cache tables (database, not application cache)

`pathway_cache` (migration `0002`) and `wiki_cache` (migration `0004`) are Supabase tables originally built as AI-output and GitHub-raw-fetch caches respectively. **Neither is read or written by any current code path** — confirmed by repo-wide grep. They are dead schema, not a live caching layer. See [`../knowledge/technical-debt.md`](../knowledge/technical-debt.md).

> **Note:** If response latency or Anthropic API cost becomes a concern beyond what content-hash caching already avoids, no framework-level caching (Redis, HTTP cache headers, CDN edge caching) is configured today — this would be new infrastructure, not a matter of enabling something already present.
