# Monitoring

> **Note:** No external monitoring/observability platform (Prometheus, Datadog, Sentry, Vercel Analytics/Speed Insights) is integrated — no such SDK or config exists in the repository. Since the monitoring/cleanup work (MLC-01–MLC-11), monitoring is **in-app**: errors and AI usage are written to Supabase tables and shown on two admin pages. Platform logs (`console.error`) still carry every error line too.

## What does exist

### Error log — `sys_errors` + `/admin/errors`

- **Every error the server sees** is written to `sys_errors` (migration `0035`) by [`lib/errors.ts`](../../../../lib/errors.ts): `kind` `expected` (validation/auth/not-found 4xx) or `unexpected` (5xx, thrown errors, stream failures), with source, scrubbed message and stack, allow-listed context IDs, the session user and `environment` (`prod`/`dev`, from `APP_ENV` or `VERCEL_ENV`). 429s are deliberately **not** recorded (they're counted in `rate_limits`), so a flood can't flood the log. Anonymous 4xx errors are recorded only while the caller's IP is within its own `anon-error` allowance (same per-IP limits as Explore), and `/api/chat` now runs its rate limit before parsing the body — closing audit finding H3 (an unauthenticated script could otherwise fill `sys_errors`).
- Sources feeding it:
  - all 23 API routes via `withErrorHandling` (`source = api/<path>`)
  - mid-stream `/api/chat` failures via `streamFailed()`
  - **`instrumentation.ts` `onRequestError`** — Server Component render, Server Action and proxy errors, with the original stack (`source = render:<routePath>` etc.; skips route handlers and `NEXT_*` redirect/notFound digests). Only loads when the server starts — restart `npm run dev` after changing it.
  - browser errors caught by `app/error.tsx`/`app/global-error.tsx`, POSTed to the public `/api/errors/client` (`source = client:<path>`)
  - `lib/rate-limit.ts` (limiter RPC failures) and `check-similar` (swallowed Anthropic failures)
  - **search/retrieval, which fails soft and logs instead of throwing:** `lib/embeddings` (the `embed` Edge Function failed after its retries — only the text count is logged, never the text), `lib/retrieval` with `step: classify` (the Haiku classifier failed; the default classification was used), and `lib/pathway-store` with `step: embed units` (a publish saved units without vectors) or `step: remove source files` (a delete could not remove a seeded pathway's originals from storage). A cluster of these rows means search is running on full text + labels only — see [`troubleshooting.md`](troubleshooting.md#search--retrieval).
- **`/admin/errors`** (admin only): the latest 50 rows, newest first, stack behind a click.
- **Retention: 30 days**, by **opportunistic purge** — after an insert, `lib/errors.ts` calls `purge_old_sys_errors(30)` at most once per server instance per hour. `pg_cron` is **not** enabled (confirmed on the dev project), so there is no scheduled job; a quiet instance simply purges on its next error.

### Usage — `ai_usage` + `/admin/usage`

- One `ai_usage` row (migration `0036`) per Claude call from `lib/ai-usage.ts`: area (explore/analyse/contribute), mode, flow, model, input/output/cache tokens, `ok`. Counts only — no prompt or reply text.
- Modes besides the chat modes: `retrieval-classify` (the Haiku classifier that runs before most Explore/Analyse replies — area follows its flow), `check-similar`, `asset-reuse`, and `seed-pathway` (one per pathway generated by `npm run seed:pathways`, `user_id` null). `areaFor()` has no case for `seed-pathway`, so seed calls are counted under **Analyse** on `/admin/usage`. Because models now differ per call site (Sonnet for replies, Haiku for classification), compare token figures by `model` as well as area.
- **`/admin/usage`** (admin only) calls `admin_usage_stats()` (migration `0038`) once: users (total, new 7d, active 7d/30d), conversations per area (`designs` by `meta.flow` + `library_conversations` — signed-in Explore only), AI calls/failures/tokens per area (input shown as total = uncached + cache read + cache write), errors per day (IST, migration `0041`) and per source split by kind. The published-pathway count is read separately (`listWikiPathways()`, i.e. the `published_pathways` view — which is empty after migration `0042` until the library is seeded). Figures are computed when the page opens.

### Other

- **`console.error`** at every swallowed-failure point (e.g. `adoption_queries` insert failures, `sys_errors`/`ai_usage` insert failures, `admin/pathways/publish`'s toolkit-asset and contributor-email steps, `contributions/[designId]` delete steps) — visible only in the platform's log viewer (Vercel function logs, or `docker logs`/CloudWatch on the AWS path).
- **`adoption_queries`** — records every companion user message tagged with the pathways it drew on, but nothing reads it back yet. See [`../business/business-rules.md`](../business/business-rules.md#monitoring-rule).
- The Google Sheets conversation log (`lib/logger.ts`) was **removed** (MLC-09); there is no longer any store of full transcripts outside `designs`/`library_conversations`.

### Rate limiting (`rate_limits`)

`lib/rate-limit.ts` keeps per-minute/per-day counters in `rate_limits` (migration `0037`): anonymous `/api/chat` (Explore) per salted IP hash (`explore`, default 20/min, 200/day), **signed-in `/api/chat` per account** (`chat-user`, default 30/min, 300/day, `CHAT_USER_RATE_LIMIT_PER_MIN`/`_PER_DAY`), plus `client-error` and `anon-error`. The limiter fails open (an RPC failure is logged to `sys_errors` and the request is allowed). There is no admin view of these counters — query the table.

## What is not present

- No health-check endpoint (no `/api/health` or equivalent route found).
- No uptime/synthetic monitoring configuration.
- No error-tracking SDK (e.g. Sentry) instrumented anywhere.
- No alerts or SLO definitions — the admin pages must be looked at; nothing notifies anyone of a spike.
- No latency measurement.

## Roadmap context

The Product Charter (`docs/raw_documents/AI DIffusion Cube - Product Charter.docx`) names "structured logging: latency, errors, per-user/per-pathway usage" in its non-functional requirements backlog. Errors and per-area usage are now covered by `sys_errors`/`ai_usage`; latency and per-pathway usage are not. See [`../knowledge/technical-debt.md#roadmap-acknowledged-gaps`](../knowledge/technical-debt.md#roadmap-acknowledged-gaps).

## Recommended (not yet implemented)

Natural next additions: a `/api/health` route for the two deploy targets' health checks (ideally also probing the `embed` Edge Function, which can be down while the app looks healthy), Vercel's built-in Analytics/Speed Insights (zero extra infra), alerting on `sys_errors` spikes (especially `lib/embeddings` / `lib/retrieval` rows, which signal silently degraded search), a count of `pathway_units` with a null embedding, and switching the remaining routes that only `console.error` a swallowed failure (e.g. `contributions/[designId]` delete steps) to `logError` so `sys_errors` sees them.
